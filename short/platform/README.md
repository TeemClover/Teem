# Torntor platform integration

Current release is an interactive **device-local demo**, not a merchant launch. The server defaults to `demo` and rejects state-changing production routes until explicitly configured. Creator uploads are saved in IndexedDB, so the Creator → review → discovery flow can be demonstrated in the same browser. It does **not** publish a visitor's files for everyone. Demo Admin is intentionally accessible for presentation, with a visible demo banner; it has no production permissions.

## Delivered

- Somchai is always first Spotlight, marked มาแรง. Four live-action drama Hero slides have real decoded MP4 trailers; desktop retains landscape artwork and opens portrait playback, mobile previews retain play/pause and mute only.
- Creator Studio `/short/studio/`: per-episode file upload, cover, synopsis, team credit, rights confirmation, free or 10-coin price, review status and feedback, preview, qualified views and estimated earnings.
- Admin `/short/admin/`: staff review, reject with notes, approve and publish, platform/episode statistics, checkout records, fees/refunds/net receipts, CSV export, integration status.
- Daily 20 coins once per Bangkok calendar day, on visit/open or while active at midnight. Coins accumulate without expiry. No retroactive grants for days a viewer did not visit. Server transaction uses server time; demo uses the device clock.
- Coins distinguish free and purchased; unlock uses free first. Unique ledger keys + row locks prevent repeated grants, repeated episode debits and repeated payment credits. Demo uses Web Locks where available.
- Payment UI supports PromptPay, TrueMoney and credit/debit via Omise.js tokenization. Demo allows success/failure simulation without entering payment details. Test/live modes never fall back to the local ledger.
- Views: video ≥3 active seconds; reading ≥10 active seconds, or completed after ≥3 seconds. Hidden tabs and paused video do not accrue time. One view per viewing session/episode; repeated reading sessions can count again. Unique signed-in users/anonymous visitor cookies counted separately. All telemetry is indicative and is not a fraud-proof billing source.

## Connect in this order

1. Create a dedicated Torntor Postgres database. Run `schema.sql` with its owner/migration role, and set `TORNTOR_DATABASE_URL` in Vercel. Do not reuse the other apps' DATABASE_URL or enable direct browser SQL/Data API/RPC access. Schema functions are invoker functions; PUBLIC access is revoked and RLS enabled. The backend connection must be a dedicated trusted owner/service role.
2. Set up Supabase Auth (can be separate from Neon DB), confirm email, invite pilot Creators and founders, set public Auth URL/key. Login verifies the bearer token against the Auth service, then reads the role from `tt_users`. A viewer can open Creator Studio via `join`; only an operator can assign `admin` through a private SQL console. Never offer a production role selector. Map existing catalog ownership in `tt_catalog_owners` for Creator analytics. Password recovery, signup UI, social login and automated payouts are separate launch work; invited accounts can sign in now.
3. Configure a **private** R2/S3 bucket and scoped credentials. Enable exact-origin browser CORS for PUT/GET (production origin and explicitly selected preview origins), Content-Type request header and Content-Length/Content-Range/ETag response headers. The upload grant expires after 5 minutes; only approved works have public discoverability. Backend verifies byte length and image/video magic bytes, creator ownership, rights declaration and immutable submission before staff approval. Keep quarantine files private. Reviewers must check rights, age guidance, sensitive content and actual audio. Malware scanning/transcoding and long-video HLS are not implemented; add them before opening unrestricted creator registration. Remove orphan quarantine assets using a scheduled operator retention job after confirming they are not referenced.
4. Create/approve the Omise merchant account and enable the desired methods (TrueMoney may need separate provider enablement). Put **test** public/secret keys into TORNTOR variables, set mode `test`, and webhook to `https://www.myclover.com/api/torntor?action=webhook`. Card data stays in Omise's hosted form; our server only receives a token. Omise API independently retrieves each charge and validates order, user, amount, currency, mode, paid/successful state before crediting. A redirect or client “success” never grants coins. PromptPay QR is generated by the provider; TrueMoney uses provider authorization. See [Omise.js](https://docs.omise.co/omise-js), [PromptPay](https://docs.omise.co/promptpay), [TrueMoney](https://docs.omise.co/truemoney-wallet), [webhooks](https://docs.omise.co/api-webhooks).
5. Exercise pending, failed, expired, successful, duplicate webhook, wrong amount/mode/user, refund and retry on a preview deployment. A unique pending checkout per user blocks duplicate charges. If a network timeout leaves an order without `charge_id`, staff must reconcile it using the provider dashboard/metadata before retry; never automatically mark a timeout failed and risk charging twice. Checkout return and “check status” independently refresh the verified charge. Refund notifications update recorded refund totals and place the affected wallet on review hold; staff reconcile already-spent coins and Creator liability before clearing `tt_users.blocked`. Transfer/payout is not automated.
6. **Before live billing, migrate existing static paid catalog content (including Somchai 4–20) to private delivery and remove public copies.** Those existing prototype files are currently public, so their browser paywall is a UX demonstration. Newly uploaded private content has server-side entitlement checks and short-lived media URLs, but that does not retrofit the static catalog. `TORNTOR_CONTENT_PROTECTED=false` blocks activation of live payments until this migration is complete. Review account/rights/refund/privacy procedures and agreed revenue split; then set live keys, mode `live`, and both activation flags true. Keep test and live data/databases separate; do not convert a test ledger into a real wallet.

## Accounting interpretation

Demo purchases are not cash. Gross topups are different from revenue earned by creators through consumed paid coins. Free grants never create Creator revenue. Creator figures are **estimates**, using paid-coin consumption × observed average net purchase value per coin × proposed 70% share. This is not FIFO accounting or a payable settlement ledger. Contracts, VAT/tax handling, refunds, provider fees and final revenue allocation must be finalized before payout. The Admin order table shows actual recorded provider fees/refunds when connected, rather than invented fee percentages. Test payments must not be reported as business income.

## Verification

`node --test --experimental-test-module-mocks short/platform/verify-api.test.mjs` checks authentication, role separation, creator ownership and origin protection. `node --test short/platform/verify-platform.test.mjs` checks Thai midnight boundaries, charge validation, activation gates, media limits and the actual SQL functions in PGlite. Supply `TORNTOR_PGLITE` pointing to an installed `@electric-sql/pglite` module. `node short/verify-platform.mjs` exercises real trailers, daily/repeated claims, three checkout simulations, Creator upload/rejection/approval/public reading, safe text rendering, metrics and 320/390/1440 layouts. `SHORT_BASE_URL` targets an existing preview/live demo. All generated upload fixtures remain isolated to the test browser.

Integration functions are implemented and SQL-tested locally, but no merchant keys, Torntor database, Auth or private storage were configured at this release. A real provider transaction and deployed SQL/auth/storage flow must pass before launch.

and authentication are connected. Demo unique readers represent this device,
not platform-wide people. No reading figures were invented or seeded.
