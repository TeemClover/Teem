# 05 · แตกซอสเดียวเป็นงานหลายแบบ

## วิธีใช้และขอบเขต

**SPLIT · คนอ่านเปลี่ยน รูปแบบเปลี่ยน แต่ข้อเท็จจริงต้องตามกลับไปที่ซอสชุดเดียวกันได้**

- **ใช้กับ:** องค์กรหรือทีมที่ต้องสื่อสารเรื่องเดียวกันให้ผู้รับหลายกลุ่ม
- **เชื่อมบทเรียน:** [บทที่ 4 · Split](/classroom/notebooklm.html)

ใช้เมื่อมีซอสองค์กรที่ตรวจแล้วและงานแรกที่ชิมแล้ว ต้องการสื่อสารเรื่องเดียวกันกับคนสามกลุ่ม เช่น ผู้ใช้บริการ คนใหม่ในทีม และผู้ประสานงาน เหมาะกับธุรกิจ โรงเรียน องค์กรไม่แสวงกำไร หรือทีมเล็ก โดยเปลี่ยนผู้รับและงานให้ตรงบริบทจริง

- **วัตถุดิบ:** `01-source-index.md`, `02-organization-source.md`, `03-style-and-quality.md`, `04-work-brief.md`, งานแรกพร้อมผลตรวจ และไฟล์อ้างอิงที่อนุญาตให้ใช้
- **ใช้คู่กับ:** ขวด 02, 03 และ 04 เป็นฐาน; ใช้ขวด 06 จัดคนทำและคนตรวจ แล้วส่งทั้งชุดผ่านขวด 07
- **สิ่งที่จะได้:** `05-output-map.md` พร้อมแผนสามงาน แล้วจึงสร้าง FAQ, คู่มือเริ่มต้น และโครงสไลด์ตามแผนที่ผู้รับผิดชอบตรวจแล้ว
- **เริ่มอย่างไร:** ระบุว่าคนแต่ละกลุ่มต้องทำอะไรต่อ เลือกข้อมูลที่แต่ละกลุ่มจำเป็นต้องเห็น แล้วแนบไฟล์นี้พร้อมวัตถุดิบและคำสั่งท้ายสูตร

จำนวนสามงานเป็นแบบฝึกตั้งต้น ไม่ใช่ข้อบังคับถาวร หากมีงานเดียวที่จำเป็น ให้ทำให้ใช้ได้ก่อน ไม่สร้างจำนวนงานเพื่อเติมช่องครบ เอกสารนี้ยังไม่อนุมัติเนื้อหาหรือการเผยแพร่แทนองค์กร

วันที่อ่านเป็นวันที่จัดทำสูตรนี้ ไม่ใช่วันที่ข้อเท็จจริงขององค์กรเริ่มมีผล เมื่อใช้จริงต้องบันทึก ID และ version ของซอสองค์กรแยกจากทะเบียนวิธีเรียนข้างต้น

## เนื้อหาหลัก

### SOURCE · สิ่งที่ต้นทางสอนไว้

- S01 ใช้ซอสเดียวแตกเป็นหลายรูปแบบ โดยรักษาข้อเท็จจริง Key Messages น้ำเสียง และ Canon; ต้องตรวจชื่อ ตัวเลข ลำดับ และข้อสรุปก่อนใช้
- S01 แยกการแก้: ผิดงานเดียวแก้งานนั้น ผิดซ้ำหลายงานกลับไปแก้ซอส ข้อมูลถูกแต่สื่อไม่เข้าใจให้เปลี่ยนรูปแบบหรือผู้รับเป้าหมาย
- S02 ให้ล็อกสิ่งที่ผ่านแล้ว ระบุสิ่งที่แก้ และบันทึกคำตัดสินใหม่กลับต้นทาง
- S03 ถือว่างานเสร็จเมื่อเปิดใช้และตรวจพฤติกรรมจริงได้ ไม่ใช่มีข้อความคำสั่งเพียงอย่างเดียว

### DERIVED · วิธีประยุกต์เป็นชุดงานขององค์กร

1. **เลือกเรื่องเดียว:** ระบุงานหรือบริการที่ต้องสื่อสารจากขวด 04 อย่าเอาคนละโครงการมาปนเพื่อให้ได้สามชิ้น
2. **แยกผู้รับ:** แต่ละงานระบุคนอ่าน คำถามที่เขาต้องได้คำตอบ และการกระทำถัดไป ใช้หลักฐานผู้ใช้ที่มี ถ้ายังไม่มีให้เขียนว่าเป็นสมมติฐาน
3. **ตรึงฐานข้อมูล:** ลง ID, version และหัวข้อ/Claim ID ของซอสทุกไฟล์ที่ใช้อ้างอิง แยกคำที่ต้องตรงกันจากคำที่ปรับให้เหมาะกับคนอ่านได้
4. **วางแผนก่อนผลิต:** เติมแผนสามแถวด้านล่างพร้อมสิทธิ์การมองเห็น คนตรวจตรวจความจำเป็นและขอบเขต แล้วจึงสร้างทีละงาน
5. **ตรวจสองรอบ:** รอบแรกตรวจแต่ละงานเทียบซอส รอบสองเทียบกันเองว่าข้อเท็จจริงและเงื่อนไขไม่เปลี่ยนตามภาชนะ
6. **เก็บผลชิม:** ให้ตัวแทนผู้รับลองตอบคำถามหรือทำขั้นตอนจริง บันทึกสิ่งที่เกิดขึ้น แก้ที่งาน/ซอส/คำตัดสินให้ตรงสาเหตุ

### แบบเติมข้อมูล · `05-output-map.md`

### คำสั่งเริ่มงาน

> อ่านซอสองค์กร ไฟล์ขวด 03–04 และสูตรนี้ ใช้เฉพาะข้อมูลที่ฉันแนบหรือชี้ตำแหน่งให้เข้าถึงได้จริง สร้าง `05-output-map.md` ก่อน โดยกำหนด FAQ สำหรับผู้ใช้บริการ คู่มือสำหรับคนใหม่ และสไลด์สำหรับผู้ประสานงานให้ตอบความต้องการที่ต่างกัน ระบุ Source ID, version และหัวข้อที่รองรับทุกงาน แยกข้อเท็จจริงจากข้อเสนอเรื่องการนำเสนอ ช่องว่างเป็น OPEN พร้อมคำถามที่จำเป็น ถ้าข้อมูลไม่พอสำหรับงานใดให้ระบุส่วนที่ทำได้และส่วนที่รอ ไม่แต่งข้อมูลเพื่อให้ครบสามงาน

เมื่อเจ้าของตรวจแผนแล้ว:

> สร้าง [Output ID] ตามแผน version [ระบุ] พร้อมรายการอ้างอิงสำหรับคนตรวจ รักษาข้อเท็จจริงและเงื่อนไขจากซอส ปรับเฉพาะวิธีอธิบายให้เหมาะกับผู้รับ ห้ามเพิ่มวัน เวลา ราคา คุณสมบัติ คำรับรอง หรือผลลัพธ์ที่ซอสไม่รองรับ ส่งเป็นไฟล์ที่เปิดใช้ได้ แล้วตรวจเทียบแผนและซอสก่อนสรุปสถานะจริง

### ตัวอย่างสมมติขนาดเล็ก

**ข้อมูลสมมติสำหรับฝึกเท่านั้น:** ทีม “ห้องแบ่งปัน” มี Source `DEMO-ORG@1.0.0` ระบุว่า “ผู้ขอใช้ห้องส่งวัตถุประสงค์และเวลาที่ต้องการให้ผู้ดูแล ผู้ดูแลยืนยันความพร้อมก่อนใช้” ยังไม่มีข้อมูลค่าบริการหรือเวลาเปิด

- FAQ: “ขอใช้ห้องอย่างไร” → อธิบายสิ่งที่ต้องส่งและการรอยืนยัน; เรื่องค่าบริการเป็น OPEN
- คู่มือคนใหม่: ตรวจว่าคำขอมีวัตถุประสงค์และเวลาที่ต้องการ แล้วส่งให้ผู้ดูแล; ห้ามอนุมัติแทน
- สไลด์ผู้ประสานงาน: แสดงเส้นทางคำขอ → ตรวจข้อมูล → ผู้ดูแลยืนยัน โดยอ้าง `DEMO-ORG@1.0.0`

ทั้งสามงานมีผู้รับต่างกัน แต่ไม่มีงานใดเปลี่ยน “ต้องรอยืนยัน” เป็น “ใช้ห้องได้ทันที”

## เกณฑ์ตรวจและวิธีแก้เมื่อผิด

| ตรวจอะไร | หลักฐานว่าผ่าน | ถ้าไม่ผ่านแก้อย่างไร |
|---|---|---|
| ใช้ซอสฉบับเดียวกัน | ทุกงานมี Source ID@version และตำแหน่งอ้างอิง | หยุดใช้ฉบับที่คลาด แล้วสร้างใหม่เฉพาะส่วนที่ได้รับผล |

| ไม่มีคำอ้างใหม่ | ชื่อ ตัวเลข เงื่อนไข และคำรับรองย้อนกลับต้นทางได้ | ลบ/ทำเครื่องหมาย OPEN และขอหลักฐานจากเจ้าของ |
| ไม่ขัดกันข้ามงาน | ตารางเทียบร่วมตรวจแล้วทุกจุด | ถ้าผิดงานเดียวแก้งานนั้น; ถ้าผิดหลายงานตรวจซอสก่อน |
| สิ่งที่ผ่านยังอยู่ | รายการ Must Keep ไม่เปลี่ยนระหว่างแก้ | จำกัดรายการแก้และตรวจเฉพาะส่วนที่กระทบ |
| ส่งให้ถูกคน | ระดับการเข้าถึงและผู้รับของแต่ละไฟล์ชัด | แยกฉบับสำหรับผู้รับก่อนส่ง ไม่อาศัยชื่อไฟล์หรือ noindex ป้องกันข้อมูล |
