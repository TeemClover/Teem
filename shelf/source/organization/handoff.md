# 07 · บรรจุงานให้คนอื่นใช้ต่อได้

## วิธีใช้และขอบเขต

**SERVE · งานจบหนึ่งรอบเมื่อผู้รับเปิดใช้ได้ รู้ข้อจำกัด และรู้ว่าจะแก้หรือทำต่อจากตรงไหน**

- **ใช้กับ:** งานที่มีไฟล์จริงพร้อมผลตรวจ และกำลังส่งให้ผู้รับหรือผู้ดูแลคนถัดไป
- **เชื่อมบทเรียน:** [บทที่ 6 · Serve](/classroom/first-web.html)

ใช้ก่อนส่งงานที่ผ่านเกณฑ์ให้ทีม ผู้ใช้บริการ ผู้เรียน หรือผู้ประสานงาน รวมถึงก่อนย้ายแชตหรือเปลี่ยนคนดูแลงาน เหมาะกับองค์กรทุกประเภท การจัดชุดส่งต่อไม่เท่ากับการอนุมัติเผยแพร่ต่อสาธารณะ

- **วัตถุดิบ:** `01-source-index.md`, `06-team-workflow.md`, ซอส/Brief/เกณฑ์ที่ Workflow อ้าง, ไฟล์ผลงานที่มีจริงและผลตรวจ, ไฟล์อ้างอิงที่ใช้จริง, รายการผู้รับและสิทธิ์, ข้อที่ยังไม่จบ; แนบขวด 05 เฉพาะถ้ามีชุดหลายงาน
- **ใช้คู่กับ:** ขวด 05 สำหรับชุดหลายงาน, ขวด 06 สำหรับวิธีทำต่อ, ขวด 08 สำหรับส่งให้รุ่นเรียนหรือผู้ดูแลคนถัดไป
- **สิ่งที่จะได้:** `07-handoff.md` พร้อมทะเบียนไฟล์ในชุดฉบับที่ตรวจแล้ว วิธีเปิดใช้ สถานะรายงาน ผลลองใช้ และทางแก้/ดูแลต่อ
- **เริ่มอย่างไร:** ให้ผู้ที่ไม่ได้สร้างงานลองเปิดชุดงานด้วยคู่มือที่เตรียมไว้ บันทึกว่าเขาติดตรงไหนก่อนถือว่าส่งต่อสำเร็จ

รูปแบบไฟล์และพื้นที่เก็บเลือกตามผู้รับจริง สูตรไม่ได้กำหนดให้ทุกงานเป็นเว็บหรือไฟล์เดียว ไม่ใส่รหัสผ่าน กุญแจ API หรือข้อมูลส่วนบุคคลเกินจำเป็นใน manifest; อธิบายวิธีขอสิทธิ์ผ่านช่องทางที่องค์กรใช้แทน

## เนื้อหาหลัก

### SOURCE · สิ่งที่ต้นทางสอนไว้

- S01 ตรวจผลงานจริงหลังออกจากแชต รวมข้อมูล ลิงก์ พฤติกรรม และบริบทผู้ใช้; การเผยแพร่เป็นขั้นที่เลือกตามงาน
- S02 เก็บสิ่งที่ทำแล้ว คำตัดสินที่ต้องรักษา ข้อมูลที่ถูกแทน งานค้าง และคำสั่งเริ่มต่อ ไม่ให้การย้ายแชตตัดความรู้ที่จำเป็นทิ้ง
- S04 สูตร README ห้ามเดาคำสั่งหรือไฟล์ที่ไม่มี และแยกคำแนะนำผู้ใช้จากบันทึกคนพัฒนา
- S03/S05 ชี้ว่าการแก้ต้องกลับไปถูกชั้น: ตัวงาน ต้นทางที่ขาด/ขัดกัน หรือคำตัดสินใหม่ของเจ้าของ

### DERIVED · ขั้นส่งมอบและดูแลต่อ

1. **เลือกฉบับที่จะส่ง:** จดไฟล์ที่มีจริงและผลตรวจของแต่ละไฟล์ แยก “พร้อมใช้ในขอบเขตนี้” ออกจาก “ร่าง” ไม่เหมารวมทั้งโฟลเดอร์ว่าผ่าน
2. **ตรึงต้นทาง:** บอก Source ID@version ที่แต่ละงานใช้ และฉบับที่ถูกแทน หากมีการแก้ต้นทางหลังสร้างงาน ให้ประเมินผลกระทบก่อนส่ง
3. **จัดทางเข้าให้ผู้รับ:** ระบุเปิดไฟล์ไหนก่อน ใช้สิทธิ์ใด ใครช่วยได้เมื่อเปิดไม่ได้ และผู้รับควรทำอะไรเป็นอย่างแรก
4. **ลองกับคนจริง:** ให้ตัวแทนผู้รับทำงานเล็กจากชุดนี้ บันทึกไฟล์/ฉบับ/โจทย์/สิ่งที่เกิดขึ้น/สิ่งที่ต้องแก้ ไม่แทนผลลองใช้ด้วยความเห็นของผู้สร้าง
5. **ส่งภายในขอบเขตที่อนุมัติแล้ว:** ตรวจทั้งเนื้อหา กลุ่มผู้รับ และสถานที่เผยแพร่ก่อนส่ง ถ้าจะขยายผู้รับหรือเผยแพร่สาธารณะ ให้คนที่มีอำนาจตรวจขอบเขตใหม่
6. **ปิดรอบและกำหนดรอบต่อ:** มอบเจ้าของข้อมูล ข้อค้าง และเหตุการณ์ที่ต้องทบทวน เมื่อได้รับ Feedback ใหม่ให้จัดประเภทก่อนแก้

### คำสั่งเริ่มงาน

> ตรวจไฟล์ที่แนบและตำแหน่งที่เข้าถึงได้จริง แล้วสร้าง `07-handoff.md` ตามสูตรนี้ ระบุ manifest, Source ID@version, ผลตรวจ, วิธีเปิดใช้, ผู้รับ, สิทธิ์ และเรื่องที่ยังไม่จบ อย่าใส่ไฟล์หรือผลทดสอบที่ยังไม่มี ถ้ายังไม่ได้ให้คนจริงลองใช้ให้ระบุ “ยังไม่ได้ลอง” พร้อมโจทย์ทดลองที่แนะนำ แยกสิ่งที่พร้อมส่งจากสิ่งที่รอข้อมูล การจัดชุดนี้ยังไม่สั่งให้เผยแพร่หรือส่งข้อความแทนฉัน

### คำสั่งเมื่อได้รับ Feedback

> เทียบ Feedback นี้กับไฟล์ฉบับที่ผู้รับใช้และซอสที่อ้าง แยกว่าเกิดจากซอสขาด/ขัด งานทำผิด การเข้าถึง หรือคำตัดสินใหม่ เสนอรายการแก้เฉพาะจุดพร้อมสิ่งที่ต้องรักษา บอกงานอื่นที่อาจได้รับผล อย่าเปลี่ยนข้อเท็จจริงตามความเห็นผู้ใช้โดยไม่ให้เจ้าของข้อมูลยืนยัน เมื่อแก้แล้วบันทึก version และผลตรวจซ้ำใน handoff

### ตัวอย่างสมมติขนาดเล็ก

ทีม “ห้องแบ่งปัน” ส่ง FAQ และคู่มือให้ผู้ดูแลคนใหม่ เขาเปิดคู่มือได้แต่ไม่รู้ว่าคำขอใช้ห้องต้องส่งให้บทบาทใด บันทึกผลเป็น “เปิดไฟล์ได้ แต่ยังทำขั้นส่งคำขอไม่ได้” หากซอสไม่ระบุผู้รับผิดชอบ ต้องกลับไปถามเจ้าของบริบทและเติมซอสก่อนแก้คู่มือ ไม่เขียนว่า “ส่งต่อสำเร็จ” เพียงเพราะอัปโหลดไฟล์แล้ว

เมื่อผู้ดูแลยืนยันบทบาทรับคำขอ จึงสร้างซอสฉบับใหม่ แก้ FAQ/คู่มือที่อ้างเรื่องนี้ และให้คนเดิมลองขั้นตอนอีกครั้ง ตัวอย่างนี้เป็นสถานการณ์สมมติ ไม่ใช่ผลการใช้งานจริง

## เกณฑ์ตรวจและวิธีแก้เมื่อผิด

| ตรวจอะไร | หลักฐานว่าผ่าน | วิธีแก้ |
|---|---|---|
| ชุดมีไฟล์ตามที่บอก | เปิด manifest เทียบไฟล์จริงได้ | ลบรายการที่ไม่มีหรือจัดทำให้ครบโดยไม่อ้างว่าเสร็จแล้ว |
| ผลตรวจผูกกับฉบับ | ทุกผลตรวจมีไฟล์@version และวันที่ | ตรวจใหม่เฉพาะฉบับ/ส่วนที่เปลี่ยนก่อนยืนยัน |
| ผู้รับเริ่มใช้ได้ | คนเป้าหมายลองงานแรกแล้วมีผลบันทึก | แก้ทางเข้า คู่มือ หรือสิทธิ์ตามจุดที่ติด |
| ข้อมูลไม่เกินสิทธิ์ผู้รับ | ฉบับที่ส่งตรงกับขอบเขตที่อนุมัติ | แยก/ตัดข้อมูลและให้คนมีอำนาจตรวจขอบเขตที่เปลี่ยน |
| ไม่มีเรื่องค้างซ่อนอยู่ | OPEN มีผลกระทบ เจ้าของ และหลักฐานที่ต้องหา | บอกข้อจำกัดข้างงานที่ผู้รับจะใช้ ไม่ฝังไว้ในแชตเก่า |
| แก้ถูกชั้น | บันทึกแยกสาเหตุและงานที่กระทบ | กลับซอสเมื่อข้อมูลขาด/ขัด; แก้งานเมื่อทำผิด; บันทึกคำตัดสินใหม่ต่างหาก |

## คำสั่งส่งต่อ

ส่งเฉพาะชุดและฉบับที่ระบุใน manifest ให้ผู้รับที่มีสิทธิ์อ่าน พร้อมสิ่งที่ยัง OPEN และงานถัดไป เมื่อผู้รับเจอปัญหาให้บันทึกไฟล์/ฉบับ/ขั้นที่ทำก่อนแก้ รักษาฉบับที่ถูกแทนไว้ตามนโยบายขององค์กรและชี้ฉบับปัจจุบันให้ชัด ใช้ผลลองใช้จริงเป็นวัตถุดิบของขวด 08 สำหรับคนหรือรุ่นถัดไป
