# คุมเสียง ภาพ และคุณภาพ — ก่อนทำงานจริง

## วิธีใช้และขอบเขต

**ใช้กับ:** AI ที่เขียน ออกแบบ หรือทำชิ้นงานทดลอง และผู้ตรวจที่ต้องอธิบายว่าอะไรผ่านหรือควรแก้

**ใส่อะไร:** `02-organization-source.md` เวอร์ชันที่ใช้จริง ตัวอย่างข้อความหรือภาพที่มีสิทธิใช้ ความชอบที่เจ้าของงานยืนยัน และงานทดลองหนึ่งชิ้น

**ได้อะไร:** `03-style-and-quality.md` — กติกาน้ำเสียง ภาพ พฤติกรรม และเกณฑ์ตรวจ พร้อมรายการสิ่งที่ล็อกและประวัติการแก้

**เชื่อมบทเรียน:** บท 2 · TASTE — `/classroom/image-ai.html`; ปรุงรสและชิมแล้วแก้ใน `/course/`; การคุมแก่นเมื่อแตกงานใน `/classroom/notebooklm.html`

**ทำก่อน:** ใช้สูตร `org-core-source` หรือมี Source ที่ตรวจกลับได้แล้ว เริ่มจากงานเล็กที่เป็นตัวแทนของงานที่จะทำ เช่น ข้อความต้อนรับหนึ่งย่อหน้า หรือภาพประกอบหนึ่งภาพ

บท TASTE ที่มีอยู่ฝึกทำโปสเตอร์ชีวิตจาก Source ของผู้เรียน สูตรนี้เป็นการประยุกต์ให้ทีม บริษัท โรงเรียน หน่วยงานสาธารณะ และองค์กรไม่แสวงกำไรใช้ตรวจงานของตนเอง ไม่ได้อ้างว่าการทำคู่มือสไตล์องค์กรเป็นการบ้านเดิมของบทนั้น

ไม่จำเป็นต้องมีโลโก้หรือคู่มือแบรนด์ก่อนเริ่ม ถ้ายังไม่มี ให้ใช้รูปแบบกลางที่อ่านง่ายและระบุว่าเป็นข้อเสนอสำหรับชิ้นทดลอง อย่าตั้งสีประจำองค์กร บุคลิก หรือมาตรฐานบริการขึ้นเอง

## เนื้อหาหลัก

### SOURCE — หลักจากต้นทางที่นำมาใช้

- น้ำเสียง ตัวอย่าง และข้อห้ามควรอยู่ใน Source เพื่อให้ส่งต่อไปกับงานได้ [S01]
- บท TASTE ใช้ข้อมูลจาก Source สร้างทิศทางภาพ แล้วตรวจว่าภาพยังตรงเรื่องและเจตนาหรือไม่ ภาพอ้างอิงบุคคลกับภาพตีความจากข้อความมีขอบเขตต่างกัน [S02]
- เมื่อแตกงานหลายรูปแบบ ข้อเท็จจริง แก่น น้ำเสียง และ Canon ต้องไม่เปลี่ยนตามรูปแบบ ถ้าผิดซ้ำหลายงานให้ดูที่ Source; ถ้าผิดเฉพาะงานให้แก้จุดนั้นและรักษาส่วนที่ผ่าน [S03]

### DERIVED — วิธีทำทีละขั้นสำหรับองค์กร

1. **เลือกผู้รับและงานทดลองหนึ่งชิ้น** ระบุว่าคนอ่านหรือคนใช้ต้องเข้าใจและทำอะไรต่อ เช่น ผู้มาใช้บริการครั้งแรกต้องรู้ขั้นตอนแรก ไม่เริ่มจากคำกว้างว่า “อยากดูดี”
2. **ล็อกสิ่งที่สไตล์ไม่มีสิทธิเปลี่ยน** ดึงชื่อ คำเฉพาะ ตัวเลข เงื่อนไข ขั้นตอนบริการ และข้อห้ามจาก Source พร้อม ID หลักฐาน ถ้ายังขัดกันให้ค้างไว้เป็น OPEN
3. **ทำให้น้ำเสียงเห็นภาพ** เลือกคำอธิบายสั้น ๆ ไม่เกินสามข้อ แต่ละข้อมีประโยคที่อยากได้ ประโยคที่ควรหลีกเลี่ยง และเหตุผลตามผู้รับ แยกตัวอย่างที่องค์กรยืนยันแล้วกับข้อเสนอของผู้ทำ
4. **กำหนดภาพเท่าที่มีหลักฐานหรือมีผู้เลือก** ระบุภาพอ้างอิงที่มีสิทธิใช้ สีหรือรูปแบบที่อนุมัติ จุดที่ต้องรักษา และสิ่งที่ทดลองได้ ถ้าไม่มีแนวทาง ให้เสนอทางเลือกกลางเพียงหนึ่งแบบเพื่อทดสอบ แล้วบันทึกว่าเป็น IDEA จนกว่าจะมีคำตัดสิน
5. **กำหนดพฤติกรรมตามชนิดงาน** เอกสารต้องสแกนหัวข้อและหาขั้นตอนต่อไปได้; งานที่กดได้ต้องมีชื่อปุ่มตรงผลที่เกิด; งานภาพหรือวิดีโอต้องมีใจความชัดตามบริบทที่เปิดดู ไม่จำเป็นต้องเพิ่มปุ่มหรือภาพเคลื่อนไหวในทุกงาน
6. **ทดลองจาก Source เวอร์ชันที่ระบุ** สร้างเพียงย่อหน้า หน้า หรือภาพตัวอย่างที่พอทดสอบเกณฑ์ได้ บันทึกชื่อชิ้นงานและสิ่งที่ผู้ตรวจเปิดดูจริง หากยังไม่ได้เปิดดูให้เขียน “ยังไม่ได้ตรวจ”
7. **ให้ feedback แบบชี้จุด** ระบุส่วนที่ผิด หลักฐานหรือกติกาที่ขัดกัน ผลต่อผู้รับ และวิธีแก้ จัดลำดับข้อมูลผิดก่อนความชอบทางภาพ แก้ทีละปัญหาหรือชุดปัญหาที่มีต้นเหตุเดียวกัน ล็อกส่วนที่ผ่าน
8. **สรุปกติกาที่ใช้ต่อได้** ถ้าต้นเหตุอยู่ใน Source ให้แก้ Source ก่อนแล้วระบุงานที่ต้องตรวจใหม่; ถ้าเป็นความผิดเฉพาะชิ้น ให้แก้ชิ้นนั้น เก็บกติกาที่ผู้มีหน้าที่ตัดสินยืนยันแล้วไว้ใน `03-style-and-quality.md` และเพิ่มเวอร์ชันเมื่อเปลี่ยนความหมาย

คำว่า “เป็นมิตร” เป็นความชอบที่ต้องทำให้ทดสอบได้ ส่วนเงื่อนไขบริการเป็นข้อเท็จจริง การปรุงสำนวนไม่ทำให้มีสิทธิเปลี่ยนเงื่อนไขนั้น

ทีมดูแลพื้นที่อ่านหนังสือสมมติมี Source ระบุว่า “ผู้ใช้ลงชื่อกับผู้ดูแลเมื่อมาถึง” [F01 จากคู่มือสมมติ S01 หัวข้อ 2] ผู้ดูแลงานเลือกน้ำเสียงสุภาพ เข้าใจง่าย ไม่เร่งเร้า [D01] แต่ยังไม่มีระบบจองและไม่ได้ให้เบอร์ติดต่อ

งานทดลองเขียนว่า “ยินดีต้อนรับ เลือกมุมอ่านที่สะดวก แล้วลงชื่อกับผู้ดูแลเมื่อมาถึง จองที่นั่งกับเราได้ตลอด 24 ชั่วโมง”

- ผ่าน: คำต้อนรับและภาษาที่อ่านง่าย
- ไม่ผ่าน: ข้อความเรื่องจองได้ตลอด 24 ชั่วโมงไม่มีหลักฐาน และลำดับเลือกที่นั่งก่อนลงชื่อไม่ได้ยืนยัน
- คำสั่งแก้: “คงคำต้อนรับและน้ำเสียงเดิม จัดขั้นตอนให้เริ่มจากลงชื่อกับผู้ดูแลตาม F01 ลบข้อความเรื่องการจอง ไม่เติมช่องทางใหม่”
- ผลแก้ตัวอย่าง: “ยินดีต้อนรับ เมื่อมาถึง กรุณาลงชื่อกับผู้ดูแลก่อนเริ่มใช้พื้นที่”
- บันทึกในกติกา: ห้ามเพิ่มระบบจอง เวลาให้บริการ หรือช่องทางติดต่อจากการคาดเดา ส่วนสีและรูปแบบภาพยังเป็น OPEN ใช้หน้าข้อความเรียบง่ายสำหรับทดลองได้

ตัวอย่างนี้สาธิตวิธีตรวจ ไม่ใช่นโยบายบริการที่ทุกองค์กรควรใช้

## เกณฑ์ตรวจและวิธีแก้เมื่อผิด

| สิ่งที่ต้องผ่าน | อาการที่พบบ่อย | วิธีแก้ |
|---|---|---|
| ข้อเท็จจริงและข้อห้ามตรง Source | สำนวนลื่นขึ้นแต่เพิ่มคำรับประกันหรือบริการ | ย้อนเทียบ L01 และหลักฐาน ลบหรือแก้เฉพาะข้อความที่เกิน |
| น้ำเสียงตรวจได้ | ใช้เพียงคำว่า “มืออาชีพ/ทันสมัย” | เติมตัวอย่างผ่านและไม่ผ่านพร้อมเหตุผลตามผู้รับ |
| ความชอบไม่ปลอมเป็นกฎเดิม | AI สร้างสีและบุคลิกองค์กรแล้วเรียกว่าอนุมัติ | เปลี่ยนเป็น IDEA ระบุผู้ตรวจและขอบเขตทดลอง |
| แก้ถูกตำแหน่ง | เปลี่ยน Source ทั้งชุดจากข้อผิดพลาดเฉพาะชิ้น | หาเหตุจากหลักฐาน ถ้า Source ถูกให้แก้เฉพาะงาน |
| รักษาส่วนที่ผ่าน | ขอ “ทำใหม่ให้ดีขึ้น” แล้วรายละเอียดที่ดีหาย | ระบุจุดแก้และรายการล็อก พร้อมตรวจซ้ำที่เกี่ยวข้อง |
| ผลตรวจตรงสิ่งที่ทำจริง | เขียนว่าทดสอบมือถือหรือเปิดวิดีโอแล้วทั้งที่ไม่ได้ทำ | เปลี่ยนเป็น “ยังไม่ได้ตรวจ” และระบุขั้นตอนตรวจที่เหลือ |

**ถือว่าพร้อมส่งต่อเมื่อ:** มี Source เวอร์ชันที่อ้างถึง ผู้รับชัด กติกาที่ตรวจได้อย่างน้อยเรื่องข้อมูลและน้ำเสียง สิ่งที่ล็อก งานทดลองหนึ่งชิ้น ผลตรวจตามที่ทำจริง และรายการ OPEN ที่ไม่ถูกนำไปอ้างเป็นข้อเท็จจริง การผ่านเกณฑ์ทดลองไม่เท่ากับการอนุมัติให้เผยแพร่ทุกช่องทาง
