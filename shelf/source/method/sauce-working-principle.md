# หลักการทำงานแบบส่งขวดซอส

## 1. สิ่งที่เจ้าของโครงการยืนยัน

> การส่งขวดซอส มันคือหลักการในการทำงานของเราเลย

การส่งต่อ Source ไม่ใช่เพียงการส่งผลงานสำเร็จหนึ่งชิ้น แต่ทำให้ผู้รับนำข้อมูลและวิธีทำงานไปใช้กับ AI ของตัวเองต่อได้ ผู้ใช้เล่าว่ามีการขอซอสสำหรับเจนภาพสินค้าให้แม่น และขอวิธีแก้เมื่อผิดด้วย

สถานะหลักฐาน: เป็นการบันทึกจากบทสนทนาของเจ้าของโครงการ ไม่ใช่ผลการทดสอบอิสระ และไม่ใช่คำรับรองว่า AI จะทำถูกทุกครั้ง

## 2. ใจความที่เรียบเรียงจากบทสนทนา

ซอสที่นำไปใช้ต่อควรช่วยตอบได้ทั้ง 3 เรื่อง:

1. **ใช้ข้อมูลอะไร:** ข้อมูลต้นทาง ภาพอ้างอิง และขอบเขตของงาน
2. **ถูกคืออะไร:** สิ่งที่ต้องรักษา เกณฑ์ตรวจงาน และข้อห้าม
3. **เมื่อผิด แก้ตรงไหน:** ระบุข้อผิดพลาด กลับไปหาต้นทางที่เกี่ยวข้อง แก้โดยรักษาส่วนที่ถูก และเก็บบทเรียนกลับลง Source

ย่อหน้านี้เป็นการสังเคราะห์เพื่อใช้งาน ไม่ใช่คำพูดตรงของผู้ใช้หรือคำพูดจากเสียงผู้บริหารบริษัท

## 3. แนวทางจัดเก็บที่นำมาใช้กับ Repo นี้

- ใช้ `/shelf/source/` เป็นที่เก็บซอสใหม่และฉบับอัปเดตต่อจากนี้
- ใช้ `/shelf/catalog.json` และ `/shelf/README.md` ค้นหาก่อนสร้างไฟล์ใหม่
- ให้ซอสแต่ละเรื่องมี ID และ path หลักที่คงที่ ไม่สร้างหลายไฟล์ที่ต่างคนต่างอ้างว่าเป็นฉบับล่าสุด
- บันทึกวันที่รวบรวม วันที่อัปเดต เวอร์ชัน แหล่งที่มา และสถานะข้อมูลแยกกัน
- การย้ายไฟล์ขึ้นชั้นไม่ใช่การตรวจยืนยันราคา เงื่อนไข หรือคำกล่าวอ้างใหม่
- ข้อมูลรอยืนยันต้องยังเป็นรอยืนยัน แม้ถูกส่งต่อไปให้ AI ตัวอื่น
- เมื่อได้หลักฐานใหม่ ให้บอกว่าเปลี่ยนข้อใด จากแหล่งไหน เมื่อไร และแก้เวอร์ชันพร้อมสารบัญ

## 4. ขอบเขตงานภาพสินค้า

หลักการนี้บันทึกเหตุผลที่ต้องส่งต่อทั้งข้อมูลอ้างอิงและวิธีแก้ แต่ **ยังไม่ใช่ซอสเจนภาพสินค้าฉบับเต็ม**: ไม่มีการแนบชุดภาพอ้างอิงที่อนุมัติ prompt ต้นฉบับ หรือประวัติแก้ภาพครบชุดในไฟล์นี้

เมื่อเพิ่มซอสงานภาพจริง ต้องนำต้นฉบับนั้นเข้ามาอ้างอิง ไม่แต่งรายละเอียดว่าเคยใช้วิธีใดสำเร็จ และไม่ใช้ภาพจากความจำแทนภาพเป้าหมายที่มีอยู่จริง

## 5. คำสั่งส่งต่อ

ใช้ Source ที่ระบุในสารบัญเป็นฐาน อ่านขอบเขตและสถานะก่อนทำงาน แยกข้อเท็จจริงจากต้นทาง ข้อเสนอของ AI และส่วนที่ยังรอยืนยัน หากพบข้อผิดพลาดให้ระบุหลักฐานและสิ่งที่ต้องแก้ ไม่เขียนทับให้ดูเหมือนข้อมูลเดิมไม่เคยต่างกัน
